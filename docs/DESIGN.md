# Navigation design

## Decisions

Use a plugin on top of DMS, with Niri retaining control of tiling, focus, scrolling, and dynamic workspace lifetime. Use DMS's existing bars, theme, launcher, and settings.

The target is a top strip of window icons and titles and a left rail of workspaces. The same plugin renders window tabs in horizontal bars and workspace icons in vertical bars. Icon assignments are shared between instances within the shell session.

## Window strip

Show tiled windows on the workspace active on the hosting bar's output, not necessarily the globally focused output. Order tiled windows by Niri's column and tile indices. Exclude floating windows; use stable ID ordering for tiled windows missing layout metadata. Pressing the left mouse button on a tab focuses that window by ID immediately; releasing does not repeat the focus request. Middle-clicking a tab requests that Niri close that exact window by ID, without focusing it first; applications may show an unsaved-work prompt. The adapter rechecks current output/workspace membership before dispatch. Middle-click is enabled only for window tabs, leaving launcher and arrow controls unchanged. Tabs show the window’s exact title beside its icon, without an added application label. Blank titles use “Untitled window”, not the app ID.

Many windows must have bounded overflow; hover shows application names and window titles through DMS’s native tooltip, with its standard single-line width limit. Test DMS's host sizing before choosing scrolling, a maximum-width strip, or an overflow menu. Do not let a growing list push other bar controls off screen.

The first implementation uses a horizontally flickable icon/title strip with arrow controls and a fixed plus button. Full-width growth defaults on, replacing the former 45% monitor cap. The natural content width grows with the list up to the hosting bar’s content-width ceiling, minus actual pill padding, sibling widget widths, and gaps. It does not stretch short lists. Disabling full-width growth restores the configurable pixel maximum. The DMS 1.6.2 adapter uses the actual content area after host margins, subtracts other visible widgets in the same section, and reserves occupied neighboring sections. Empty center containers do not constrain growth. Center placement uses a symmetric budget around the bar midpoint; unusual DMS centering modes still need live validation. DMS 1.6.2's `sectionAvailablePrimarySize` is not a remaining-width contract and is not used; `BarGeometry.qml` isolates the inspected section ancestry and geometry dependencies. A newly active window is scrolled into view. During content-width growth, automatic reveal waits until the animation settles, while scroll offsets still clamp to valid bounds. The final reveal also runs when growth finishes beyond the width ceiling, where viewport width may already have stopped changing. Arrows or tab dragging suspend active-window following until focus changes, so title/layout snapshots do not interrupt manual browsing. Geometry changes clamp the offset and reveal the active tab only while following it. Positionless tiled windows follow positioned windows in ID order; floating windows are excluded. Arrows are hidden until tabs plus the launcher exceed the width ceiling; only then do they reserve space. During width growth, overflow compares the animated content demand against the actual assigned strip width, avoiding temporary arrows while an otherwise fitting tab is revealed. Removal uses the smaller live content width immediately, and a narrower hosting allocation still enables arrows. An empty strip has just the launcher button, with no label or extra gaps.

The plus button invokes DMS's existing launcher. Niri handles placement; application behavior and window rules can affect whether a new window appears and where it goes.

The inspected launcher APIs choose the globally focused output and take no screen argument. The plugin preserves that behavior for now; it does not force monitor focus when opening the launcher.

Buttons use the hosting bar’s full `barThickness`, centered by DMS’s unclipped content loader. A scoped binding sets the horizontal host pill’s `widgetThickness` to `barThickness`, so its background and outline also fill the height. The host pill is identified by its content component rather than child order; vertical instances retain DMS sizing. The DMS Size control sets bar height, whereas widget padding is horizontal for this plugin.

Workspace changes on the hosting output trigger a short fade and upward settle of the incoming horizontal tabs, keyed by the active workspace's session-local Niri ID. The live window model and focus update immediately; rapid switches restart the entrance rather than queueing transitions. Title, focus, and layout snapshots within one workspace do not restart the entrance. The natural content width eases separately, retaining independent tab widths and applying the hosting width ceiling immediately. Empty workspaces settle to the launcher-only strip. Animation duration and easing use DMS's theme, including its disabled-animation setting. The launcher and overflow controls do not fade or slide.

Window tabs use an incremental model keyed by live Niri window ID. Updating titles, focus, or geometry keeps existing delegates; opening, closing, and reordering edit the model in place. Row position transitions slide surviving tabs into the new layout, with a brief fade for added tabs. Closed tabs leave immediately when reactive state removes them, while neighbors slide into the gap. These transitions follow the same DMS timing and disabled-animation setting as workspace transitions. Tab widths retain the independent monitor-based scale.

Left-dragging a tab past the platform drag threshold moves its visual under the pointer while neighboring tabs slide aside to open its proposed slot. There is no placement marker. Focus activates on the initial left press, including when it becomes a drag. Holding it near a viewport edge scrolls overflow. Releasing inside the window viewport requests an insertion relative to another live window ID and retains the preview gap while Niri confirms the reorder; releasing outside cancels and restores the original tab positions. Workspace/output changes or structural list changes cancel the gesture. The preview uses each tab’s own width and leaves unrelated tabs in place. Neighbors move aside once the dragged tab’s leading edge overlaps 50% of their width in either direction. Targeting uses the dragged rectangle, including its grab offset and overflow scroll, against original tab geometry. Automatic focus-follow scrolling is deferred while the mouse remains held to avoid moving the pressed tab beneath the pointer. Tabs do not store a separate persistent order.

The adapter realizes a drop through adjacent swaps, awaiting reactive focus and layout confirmation for each step. Within one stack it uses window-up/down actions; between columns it first selects the intended neighboring tile, then the dragged tile, and uses Niri’s left/right swap action. Column window counts remain intact while their occupants can change; windows can take the destination column’s dimensions. Pending moves cancel on missing IDs, unexpected order/layout changes, explicit navigation/close, output/workspace changes, socket rejection, or a 1.5-second acknowledgment timeout. Focus staging does not scroll the viewport; the final active window is revealed when the operation finishes. Niri remains the source of ordering truth.

## Browser favicons

Helium window entries use the active browser tab's favicon when TabCtl is available. A shared `state/BrowserFavicons` singleton runs a read-only Python/Gio subscriber to TabCtl's `ListTabsWithIcons` method and `TabsUpdated`/D-Bus owner-change signals. It does not poll tabs, invoke tab actions, or open another Niri connection. `NiriState` combines those snapshots with DMS's existing reactive window state. Favicon bindings update separately from the strip's incremental tab model, preserving geometry, title text, ordering, and delegate identity.

Browser window IDs do not identify Niri windows. Match exact active-tab titles across all Helium Niri windows (including other outputs/workspaces and floating windows) and active Helium tabs across profiles. Strip only the final ` - Helium` window-title suffix. Assign a favicon only when every matching active tab supplies the same nonempty icon source; duplicate titles can safely share that artwork without identifying which browser window belongs to which Niri window. Never choose a duplicate by focus or list order and never persist associations. Unmatched, empty, customized, or conflicting matches fall back to the normal application icon. The initial integration deliberately supports the `helium` app ID only.

QML loads HTTP(S) favicons directly from the browser-provided URL, with normal Qt image caching. A bounded inline image can be decoded into a private temporary file by the bridge; those files disappear when the subscriber exits normally. Browser-internal image URLs are unsupported. Keep the application icon visible until the favicon is ready, and restore it on a missing/error source. No domain-derived guesses or third-party favicon service are used. TabCtl extension 2.3.0 omits favicon-only notifications; perform one extra read two seconds after a tab-change event, rather than continuous polling. Later favicon-only updates still need an upstream notification fix.

## Browser pages as windows

The optional `extensions/window-tabs` Manifest V3 extension moves newly created tabs from multi-tab normal windows into their own normal windows using browser tab IDs. It moves the existing tab rather than reopening its URL. This keeps Niri windows as the navigation model; the plugin does not gain a separate browser-tab list or browser-control connection. Single-tab windows and popups are left alone. The toolbar action persists an enabled preference; loading/resuming does not sweep existing tabs. Only storage permission is needed, with no page inspection or content scripts.

Serial event processing reduces burst races. Creation-time activation and current source/tab focus determine the destination's focus request; the compositor remains responsible for placement and actual focus. Private destinations retain private status when incognito access is enabled. Browser-restored tabs can be detached if creation events are emitted; pause before restoring a session to retain grouped tabs. Native tab creation precedes detachment, so transient tab-strip/focus changes remain possible. Group, pin, split-view, login-flow, and runtime focus compatibility require Helium validation. See the [extension guide](../extensions/window-tabs/README.md).

## Workspace rail

Show the output's workspaces in Niri order. Preserve normal dynamic workspace behavior, including the trailing empty workspace. An ordinary empty workspace can remain while active; do not forcibly delete workspaces or equate every empty workspace with an immediately removed one.

Use workspace IDs for session-local icon assignments. The local `state/WorkspaceIcons` singleton shares reactive assignments between plugin instances; `NiriState` reconciles it against all outputs so one monitor cannot discard another's icons. Remove an assignment when its workspace leaves Niri's state. Do not key icons by numeric position or persist runtime IDs across sessions. Assigning an icon never names or retains a workspace. A shell restart resets assignments, and compositor unavailability clears them. A compositor reconnect that reuses IDs without an observed unavailable/empty snapshot can retain stale assignments; detecting a compositor-session generation remains future work.

Use DMS's bundled Material Symbols Rounded font through `DankIcon`, with a single theme color and active-state primary color. A curated set of 100 symbols covers browser, terminal, development, files, communication, media, devices, planning, travel, nature, and general workspace uses. This requires no added icon downloads or multi-color application assets. A workspace without windows initially uses `empty_dashboard`; its first observed window seeds a category icon. When first loading into an existing session, choose the lowest window ID as an approximation of the earliest opened window. Floating windows can seed a workspace icon. Retain the seed when that window closes or other applications arrive. Firefox/Helium and several common browser IDs map to `web`; the initial classifier is deliberately small, with `desktop_windows` for unknown applications. Broader desktop-entry/category inference is future work.

Left-click focuses the live workspace ID through DMS's existing Niri service. Right-click opens `DankPopout` beside the hosting bar on its output, using DMS’s `getPopupTriggerPosition` to clear the bar and its configured popup gap while retaining the clicked button’s vertical position. A loader-sized outer Item holds an inset picker, so DMS’s content Loader cannot override the picker’s padded width. Its picker uses DMS text fields, colors, and scrollbars; selections update immediately and keep the picker open so the current choice can be pinned. Escape or an outside click dismisses it; workspace removal/output movement dismisses stale editing. The 336-pixel-wide picker has a 264-pixel-tall icon grid (six rows), searchable by symbol name, with a bounded pinned section first. Right-click a picker icon to pin/unpin it. Only the ordered favorite symbol names are persisted using DMS's plugin settings; favorites never represent persistent workspaces. The picker contains the workspace heading, search, pinned icons, and all-icons grid; it has no pin-current or automatic-reset buttons and no pinning help text.

The rail preserves live-ID delegates across state snapshots, reveals an activated workspace, and retains manual overflow browsing on snapshots without an active-workspace change. Its height grows with the workspace list until the hosting bar's available primary-axis space is exhausted, accounting for sibling widgets, neighboring sections, gaps, and pill padding through `BarGeometry`. Wheel/touch scrolling browses the rail; workspace activation requires clicking. The trailing empty workspace is itself navigable, so the rail does not add a separate plus button.

## Milestones

1. **Load the scaffold:** validate horizontal/vertical placement, settings, service updates, and error-free reload in the actual DMS session.
2. **Window navigation:** implemented output-aware filtering, layout ordering, title buttons, active state, bounded overflow, and launcher action; rendering verified in DMS 1.6.2; click and overflow interaction checks remain.
3. **Workspace navigation:** implemented output-aware, bounded scrolling buttons and active state; visible DMS/multi-monitor validation remains.
4. **Workspace icons:** implemented monochrome categories, editing, shared session assignments, removal cleanup, and persistent picker favorites; broader automatic classification remains.
5. **Polish:** keyboard access where supported, hover labels, urgency indication, and multi-monitor/reconnect behavior.

## Proportional icon/title tabs

Use DMS `Paths.getAppIcon`, desktop-entry lookup, and Quickshell `IconImage` (as used by DMS’s focused-window widget); unresolved icons receive a generic window icon. Show the exact window title beside the icon, eliding long text. Do not prepend or append the app name. Titles supplied by applications are not heuristically rewritten; titles and hover labels render literal plain text, including strings that resemble HTML.

Use Niri `layout.tile_size[0]` (visual width including compositor decorations), falling back to `window_size[0]` if necessary. Width data remains in the Niri adapter's pure model. Floating windows do not enter the strip model.

Use a configurable scale, defaulting to 240 tab pixels per monitor-width window. The plugin’s Window tab width slider allows 120–480 pixels and adjusts existing tabs reactively. Each tab independently has a readability minimum of 96 pixels (or 1.5 times button height plus 24 if larger). Tiny tabs therefore depart from exact ratios, but adding, shrinking, or removing one window never changes another window's width. Missing geometry uses a monitor-wide fallback, also independent of the list. The prior average/minimum-based shared scale caused unrelated tabs to expand and must not be restored.

Recalculate scroll offsets from accumulated variable widths, and reveal the active tab after geometry changes. Overflow scrolls within the configured strip ceiling. Stacked windows in one column appear as separate tabs with their individual widths; this is not a two-dimensional layout map.

## Editor tooling

Language-server imports use a local source snapshot and metadata generated by Quickshell’s own scanner, preserving JavaScript helpers and assets needed by relative imports. Nested UI components declare bound creation scopes so outer IDs resolve explicitly in both Qt and the language server. This editor-only helper never instantiates DMS services; generated metadata is persistent across reboot and refreshed explicitly after upgrades. Refreshes stage the snapshot and metadata before replacing the previous setup. Source/tooling path overlap is rejected, and generation or publication failures preserve the previous artifacts. See the development guide.


## Hover and tooltip behavior

The horizontal DMS pill disables `enableBackgroundHover` and `enableCursor`, matching DMS 1.6.2 RunningApps. Individual navigation buttons retain selected, hover, and press styling. The pill background no longer switches to the host hover color while the mouse remains over the strip.

Buttons request tooltips after 500 ms; one shared lazy `DankTooltip` loader in the strip supplies the native background, border, font, transparency, and screen clamping. Exit, press, disabling a button, hiding it, or scrolling dismisses the tooltip. Dismissal checks the owning button so an old button cannot clear a newer tooltip. Hover text is `Application name • Window title`, using DMS `Paths.getAppName` with desktop-entry lookup (falling back to the app ID). Missing application identity leaves just the title. The tab remains title-only. The inspected DMS `StyledText` renders plain text, preserving literal application titles. Native tooltips are single-line and capped at 300 pixels; long titles can elide there too.

Application icons (including the generic application-window fallback) use 85% of their former height/width allowance with a 12-pixel floor. Control glyphs and button dimensions retain their sizes.

Favicons use 85% of the resulting application-icon size, rounded down to whole pixels, and remain horizontally centered in the original icon slot with a one-logical-pixel downward optical adjustment. This balances dense website artwork against desktop icons while preserving title spacing and fallback-icon geometry.


## Wheel navigation

Wheel input anywhere over the horizontal strip focuses Niri's previous/next column on the hosting output. Up/left requests the previous column and down/right the next, following DMS reverse scrolling. The plugin’s `reverseScroll` setting defaults to false to follow DMS’s normal direction. Enabling it reverses that direction; the toggle applies on top of DMS’s global reverse-scrolling preference. Changing it clears partial wheel input so the next gesture uses the new direction. `NiriState` owns the inspected DMS `moveColumnLeft(outputName)`/`moveColumnRight(outputName)` calls, which send focus-column actions and focus the hosting monitor if necessary. This follows Niri column navigation, including its handling of stacks and column boundaries, rather than wrapping through the tab model.

Angle-based input always uses 120 units per step, including events with pixel metadata; pixel-only input uses 50 pixels per step. Changing pixel metadata does not reset accumulated angle input. There is no timed cooldown: every complete step is sent immediately, including multiple steps in a coalesced event, and partial input is retained. Input is consumed even during accumulation to avoid also scrolling the tab Flickable or triggering the host's workspace behavior. A wheel-only MouseArea accepts no buttons, preserving tab clicks and dragging. Arrow buttons and dragging continue to browse overflow without changing compositor focus.

Held window tabs paint an opaque `Theme.surfaceContainerHigh` base beneath their normal primary highlight, starting with the left press and continuing throughout dragging. The surface alpha is forced to one independently of theme transparency; release or cancellation restores the normal background. Neighbor tabs retain their usual styling.
